# GitHub 用户管理后台 需求文档（PRD）

- 版本：v0.3
- 日期：2026-11-10
- 状态：已确认，可以进入开发（部署方案在功能完成后另行讨论）
- 变更记录：
  - v0.2：取消 Go 后端，改为在现有技术栈（Hono + tRPC + Prisma）上实现
  - v0.3：确认开放注册、物理删除；新增 GitHub 模糊搜索（REQ-02），后面的需求编号顺延

## 1. 背景与目标

做一个内部管理后台：管理员输入关键字搜索 GitHub 用户，选中后查看这个人的公开资料，确认后存进自己的数据库，之后可以在后台查看、修改、删除这些记录，也可以从 GitHub 重新同步最新资料。

目标：
1. 管理员不用打开 GitHub，在后台就能搜到一个人并查看他的公开资料。
2. 查到的资料可以一键存进数据库，形成自己维护的 GitHub 用户名单。
3. 名单支持增、删、改、查，并能随时从 GitHub 刷新数据。

## 2. 范围

### 2.1 本期要做
- 前端：在现有 `apps/web`（Next.js 16）中实现管理后台页面。
- 后端：在现有 `apps/server`（Hono）和 `packages/api`（tRPC）中新增接口，负责调用 GitHub API 和读写数据库。
- 数据库：沿用 PostgreSQL + Prisma，在 `packages/db` 中新增数据表。
- 登录和注册：沿用现有的 Better Auth，**开放注册**，只有登录的用户能使用后台。

### 2.2 本期不做
- 移动端（`apps/native`）不接入本功能。
- 不同步用户的仓库、提交、组织等详细数据，只存个人资料。
- 不做定时自动同步，只支持手动同步。
- 不做多角色权限，所有登录用户权限相同。
- 不做生产部署，本期只保证本地开发可用。部署方案在功能完成后另行讨论。

## 3. 用户与使用场景

| 角色 | 说明 |
| --- | --- |
| 管理员 | 唯一角色，任何人注册后都是管理员。登录后可以搜索 GitHub 用户、查看资料、加入名单、编辑备注和标签、同步、删除。 |

典型流程：
1. 管理员注册或登录后台，进入「GitHub 用户」页面。
2. 点击「添加用户」，输入关键字 `linus`，点击「搜索」。
3. 页面列出匹配的 GitHub 用户（头像和用户名），每页 10 条。
4. 点击其中的 `torvalds`，页面显示头像、昵称、简介、公司、所在地、粉丝数、公开仓库数等完整资料。
5. 确认无误后点击「加入数据库」，记录出现在列表中。
6. 之后可以在列表或详情页给这条记录加备注和标签、从 GitHub 同步最新资料，或者删除。

## 4. 功能需求

每条需求带编号，方便拆分成 `specs/`。优先级：P0 必须做，P1 本期尽量做。

### REQ-01 注册与登录（P0）
- 用户故事：作为管理员，我可以自己注册账号；后台只有登录后才能使用。
- 说明：
  - 使用邮箱和密码注册、登录，沿用现有的 Better Auth（挂在 `apps/server` 的 `/api/auth/*` 下），以及 web 端现有 `/login` 页面里的登录和注册表单。
  - **开放注册**：任何人都可以注册，注册成功后自动登录。所有用户权限相同。
  - 防滥用：开启 Better Auth 自带的限流（`rateLimit.enabled: true`，开发环境也开启），注册和登录接口每个 IP 每分钟最多 5 次。
  - 密码最少 8 位，邮箱格式校验（现有表单已有，保持一致）。
  - 未登录时访问任何后台页面，都跳转到 `/login`。
  - 后台右上角显示当前用户，可以退出登录（现有的 `user-menu` 组件）。
  - 本功能的所有 tRPC 接口都使用 `protectedProcedure`。
- 验收标准：
  - [ ] 新用户注册成功后自动登录，进入 `/github-users`。
  - [ ] 用已注册的邮箱再次注册，提示「该邮箱已注册」。
  - [ ] 同一 IP 1 分钟内第 6 次请求注册或登录接口，返回 `429`，前端提示「操作过于频繁，请稍后再试」。
  - [ ] 未登录访问 `/github-users` 会跳转到 `/login`。
  - [ ] 未登录直接调用本功能的 tRPC 接口，返回 `UNAUTHORIZED`。
  - [ ] 退出登录后，再调用接口返回 `UNAUTHORIZED`。

### REQ-02 模糊搜索 GitHub 用户（P0）
- 用户故事：作为管理员，我只记得对方用户名或昵称的一部分，输入关键字就能列出可能的人，再从中挑选。
- 说明：
  - 这是「添加用户」页面的入口：一个搜索框加一个「搜索」按钮，按回车也可以搜索。**不做边输入边搜索**，因为 GitHub 搜索接口的额度很少（见 6.3 节）。
  - 关键字去掉首尾空格后为 1 到 100 个字符。前端表单和 tRPC 接口共用同一个 Zod 校验规则。
  - 服务端调用 GitHub 接口 `GET https://api.github.com/search/users?q={关键字}+type:user&per_page=10&page={页码}`。只搜个人用户，不包括组织；GitHub 会在用户名、昵称、公开邮箱中匹配。**浏览器不直接请求 GitHub**。
  - 结果列表每行显示头像、用户名、GitHub 主页链接。如果这个用户已经在名单里，标出「已在名单中」（服务端按 `githubId` 批量查询数据库）。
  - 用户名和关键字完全相同（不区分大小写）的那一条排在第一位，并标出「精确匹配」。
  - 分页：每页 10 条，显示总数和「上一页」「下一页」。GitHub 最多只返回前 1000 条结果，超出时提示「结果太多，请输入更具体的关键字」。
  - 搜索结果不写数据库。点击某一行进入 REQ-03 的资料预览。
  - 关键字和页码要体现在 URL 参数里，从资料预览返回时保留之前的搜索结果。
- 验收标准：
  - [ ] 输入 `linus` 搜索，2 秒内（正常网络下）列出匹配的用户，每页 10 条，并显示总数。
  - [ ] 输入 `torvalds` 搜索，`torvalds` 排在第一位并标出「精确匹配」。
  - [ ] 已在名单中的用户，在结果中标出「已在名单中」。
  - [ ] 没有结果时显示「没有找到匹配的 GitHub 用户」。
  - [ ] 关键字为空或超过 100 个字符时，前端直接提示，不发请求。
  - [ ] 搜索额度用完时，提示「GitHub 搜索过于频繁，请在 HH:mm:ss 之后重试」。
  - [ ] 翻页正确；从资料预览返回后，关键字和页码保持不变。

### REQ-03 查看 GitHub 用户资料（P0）
- 用户故事：作为管理员，我在搜索结果中点击某个人，就能看到他的完整公开资料。
- 说明：
  - 从 REQ-02 的搜索结果点击进入。也支持直接访问 `/github-users/new?username=xxx`，方便从别处粘贴链接。
  - 服务端调用 GitHub 接口 `GET https://api.github.com/users/{username}` 获取完整资料。
  - 用户名格式校验规则和 GitHub 一致：1 到 39 个字符，只能包含字母、数字和连字符 `-`，不能以连字符开头或结尾，不能出现连续两个连字符。
  - 查询结果只用于预览，**这一步不写数据库**。
  - 资料卡片展示：头像、用户名（login）、昵称、简介、公司、博客、所在地、公开邮箱、Twitter、公开仓库数、公开 Gist 数、粉丝数、关注数、GitHub 注册时间、GitHub 主页链接。
  - 如果这个用户已经在数据库里，卡片上标出「已在名单中」，并提供「查看」链接，不再显示「加入数据库」按钮。
  - 卡片上提供「返回搜索结果」。
- 验收标准：
  - [ ] 点击搜索结果中的某个用户，2 秒内（正常网络下）显示完整资料卡片。
  - [ ] 直接访问 `?username=` 指向一个不存在的用户名，提示「GitHub 上没有找到该用户」。
  - [ ] `?username=` 的格式不合法时，提示格式错误，不发请求。
  - [ ] GitHub 限流时，提示「GitHub 请求过于频繁，请在 HH:mm 之后重试」，时间取自 GitHub 返回的重置时间。
  - [ ] GitHub 超时或不可用时，提示「GitHub 暂时无法访问，请稍后重试」。
  - [ ] 已在名单中的用户，显示「已在名单中」和「查看」链接。

### REQ-04 加入数据库（P0）
- 用户故事：作为管理员，我确认资料没问题后，点击一下就能存进名单。
- 说明：
  - 前端只提交用户名，服务端**重新从 GitHub 拉一次最新资料再保存**，不信任前端传来的资料内容。
  - 以 GitHub 的数字 ID（`githubId`）判断是否重复。GitHub 用户名可以改，但数字 ID 不变。
  - 保存时记录是哪个管理员添加的，取 `ctx.session.user.id`。
- 验收标准：
  - [ ] 点击「加入数据库」后，提示「已添加」，列表里出现这条记录。
  - [ ] 重复添加同一个用户，返回 `CONFLICT`，提示「该用户已在名单中」。
  - [ ] 用户名大小写不同（如 `Torvalds` 和 `torvalds`）视为同一个人。
  - [ ] 数据库里保存的资料和 GitHub 当前的资料一致。

### REQ-05 名单列表（P0）
- 用户故事：作为管理员，我能看到所有已保存的用户，并能快速找到某个人。
- 说明：
  - 表格列：头像、用户名、昵称、公司、所在地、粉丝数、公开仓库数、标签、最后同步时间、操作。
  - 支持按关键字过滤，关键字匹配用户名、昵称、公司、备注（不区分大小写）。这里只在本地数据库中过滤，不请求 GitHub。
  - 支持按标签过滤。
  - 支持按添加时间、粉丝数、最后同步时间排序，默认按添加时间倒序。
  - 分页由服务端完成，每页默认 20 条，可选 10、20、50 条。
  - 筛选、排序和页码要体现在 URL 参数里，刷新页面后保持不变。
  - 名单为空时显示空状态，并提供「添加用户」入口。
- 验收标准：
  - [ ] 1000 条数据时，列表接口响应时间小于 300ms。
  - [ ] 关键字过滤、标签过滤、排序、分页能组合使用，结果正确。
  - [ ] 刷新页面后，筛选条件和页码保持不变。

### REQ-06 用户详情（P0）
- 用户故事：作为管理员，我能看到某个用户保存下来的完整资料和后台信息。
- 说明：
  - 展示 REQ-03 中列出的全部 GitHub 资料。
  - 另外展示后台字段：备注、标签、添加人、添加时间、最后同步时间。
- 验收标准：
  - [ ] 访问 `/github-users/{id}` 能看到完整资料。
  - [ ] 访问不存在的 ID，显示「记录不存在」页面。

### REQ-07 修改（P0）
- 用户故事：作为管理员，我能给保存的用户加备注、打标签，方便分类管理。
- 说明：
  - **只有后台字段可以修改**：备注（`remark`，最多 500 字）和标签（`tags`，最多 10 个，每个最多 20 字，自动去掉首尾空格并去重）。
  - 来自 GitHub 的字段（昵称、简介、粉丝数等）**不允许手工修改**，只能通过「同步」更新，保证数据和 GitHub 一致。
- 验收标准：
  - [ ] 修改备注和标签后保存，刷新页面数据仍在。
  - [ ] 超出长度或数量限制时，前端提示，接口返回 `BAD_REQUEST`。
  - [ ] 接口的输入校验只接受 `remark` 和 `tags`，GitHub 字段无法通过修改接口改动。

### REQ-08 从 GitHub 同步（P0）
- 用户故事：作为管理员，我能把某个用户的资料刷新成 GitHub 上的最新数据。
- 说明：
  - 在列表行和详情页都提供「同步」按钮。
  - 按 `githubId` 调用 GitHub 接口 `GET https://api.github.com/user/{id}` 拉取资料，这样即使对方改了用户名也能同步到。
  - 同步只覆盖 GitHub 字段，备注和标签保持不变；成功后更新「最后同步时间」。
- 验收标准：
  - [ ] 同步后，资料和 GitHub 当前数据一致，备注和标签没有变化。
  - [ ] 对方改名后，同步能拿到新的用户名。
  - [ ] GitHub 账号已注销（返回 404）时，提示「该账号在 GitHub 上已不存在」，本地记录保留。

### REQ-09 删除（P0）
- 用户故事：作为管理员，我能把不再关注的用户从名单里删掉。
- 说明：
  - 在列表行和详情页都提供「删除」按钮。
  - 删除前弹出确认框，确认框里显示要删除的用户名，并提示「删除后无法恢复，备注和标签会一起删除」。
  - **采用物理删除**，直接从数据库删掉记录，不做回收站。删错了可以重新搜索并添加，GitHub 资料能找回，但备注和标签会丢失。
- 验收标准：
  - [ ] 确认后记录从列表中消失，提示「已删除」，数据库中这条记录已不存在。
  - [ ] 点击取消，不发送删除请求。
  - [ ] 删除一个已经不存在的记录，返回 `NOT_FOUND`，前端提示后刷新列表。
  - [ ] 删除后可以重新添加同一个 GitHub 用户。

### REQ-10 批量删除（P1）
- 说明：列表支持勾选多条记录后批量删除，同样是物理删除；确认框中显示要删除的数量。
- 验收标准：
  - [ ] 勾选 N 条记录后批量删除，N 条记录全部消失。

## 5. 数据模型

新增 Prisma 模型，放在单独的文件 `packages/db/prisma/schema/github-user.prisma`。不要写进 `auth.prisma`，因为执行 `auth:generate` 时会覆盖它。

```prisma
model GithubUser {
  id              Int      @id @default(autoincrement())
  githubId        Int      @unique                 // GitHub 数字 ID，用来判重和同步
  login           String                           // GitHub 用户名（可能改名，所以不设唯一）
  name            String?
  avatarUrl       String
  htmlUrl         String
  bio             String?
  company         String?
  blog            String?
  location        String?
  email           String?
  twitterUsername String?
  publicRepos     Int      @default(0)
  publicGists     Int      @default(0)
  followers       Int      @default(0)
  following       Int      @default(0)
  githubCreatedAt DateTime
  githubUpdatedAt DateTime
  remark          String?  @db.VarChar(500)        // 后台备注
  tags            String[] @default([])            // 后台标签
  createdById     String                           // 添加人，对应 user.id
  syncedAt        DateTime                         // 最后一次从 GitHub 同步的时间
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  @@index([login])
  @@index([tags], type: Gin)
  @@index([createdAt])
  @@map("github_user")
}
```

说明：
- **采用物理删除，所以没有 `deletedAt` 字段**。`githubId` 的唯一约束直接生效，删除后重新添加不会冲突。
- **按用户名判断「已在名单中」时不区分大小写**，查询时用 `mode: "insensitive"`。
- **`login` 不设唯一约束**：用户 A 改名后，用户 B 可能会注册 A 的旧用户名。所以真正用来判重的是 `githubId`。
- **`createdById` 不建外键关联**：建关联需要在 `auth.prisma` 的 `User` 模型上加反向字段，而这个字段会在下次执行 `auth:generate` 时被覆盖掉。添加人的账号被删后，详情页的添加人显示为「已删除的用户」。
- **`githubId` 用 `Int`**：GitHub 用户 ID 目前在 3 亿左右，`Int` 的上限是 21 亿，暂时够用。如果担心以后超出，可以改成 `BigInt`，代价是前端需要额外处理序列化。
- **从本功能开始用迁移管理表结构**：执行 `pnpm run db:migrate` 生成迁移文件并提交，不再用 `db:push`。

### 6.3 GitHub 调用规则
- 请求头带上 `Accept: application/vnd.github+json`、`X-GitHub-Api-Version: 2022-11-28`、`User-Agent: zyk-aws-admin`；配置了 `GITHUB_TOKEN` 时加上 `Authorization: Bearer <token>`。
- 单次请求超时 10 秒（使用 `AbortSignal.timeout`）。
- 返回数据先经过 Zod 校验再使用。
- 额度（以 GitHub 官方为准）：

| 接口类型 | 没有 token | 有 token |
| --- | --- | --- |
| 搜索 `/search/users` | 每分钟 10 次 | 每分钟 30 次 |
| 用户资料 `/users/*`、`/user/*` | 每小时 60 次 | 每小时 5000 次 |

两种额度分开计算，响应头 `x-ratelimit-resource` 会说明是哪一种。开放注册后所有用户共用同一个 token 的额度，所以要靠缓存和「按钮触发搜索」来节省额度。

- 错误映射：

| GitHub 情况 | tRPC 错误码 | `appCode` |
| --- | --- | --- |
| 404 | `NOT_FOUND` | `GITHUB_USER_NOT_FOUND` |
| 403 或 429，且 `x-ratelimit-remaining` 为 0 | `TOO_MANY_REQUESTS` | 搜索接口为 `GITHUB_SEARCH_RATE_LIMITED`，其他为 `GITHUB_RATE_LIMITED`；都带上 `resetAt` |
| 422（搜索关键字不合法） | `BAD_REQUEST` | `GITHUB_SEARCH_INVALID` |
| 超时、网络错误或 5xx | `BAD_GATEWAY` | `GITHUB_UNAVAILABLE` |

- 缓存：搜索结果（按「关键字小写 + 页码」）和资料查询结果（按「用户名小写」）都在内存中缓存 60 秒。添加和同步接口不走缓存。缓存条目最多 500 条，超出时淘汰最早的。

### 6.4 前端改动（`apps/web`）
- 页面：
  - `/login`：已有，保留登录和注册两个表单。登录或注册成功后跳转到 `/github-users`。注册和登录被限流时显示对应提示。
  - `/github-users`：名单列表页，对应 REQ-05、REQ-09、REQ-10。
  - `/github-users/new`：搜索、资料预览、添加，对应 REQ-02、REQ-03、REQ-04。用 URL 参数区分状态：`?q=&page=` 显示搜索结果，`?username=` 显示资料预览。
  - `/github-users/[id]`：详情和编辑页，对应 REQ-06 到 REQ-09。
  - `/` 和 `/dashboard`：登录后跳转到 `/github-users`。
  - `components/header.tsx`：导航增加「GitHub 用户」。
- 登录校验：沿用现有 `/dashboard` 的写法，在服务端组件里调用 `authClient.getSession({ headers })`，没有会话就跳转到 `/login`。
- 数据请求：沿用现有的 `useTRPC()` + TanStack Query；增删改成功后让对应的列表和详情缓存失效。搜索查询设置 `staleTime: 60_000`，并关闭窗口聚焦时自动重新请求，避免浪费搜索额度。
- 表单：使用 TanStack Form + Zod；用户名和关键字的校验规则从 `packages/api` 共享。
- 错误提示：根据 `error.data.appCode` 显示第 4 节中规定的提示文字。`utils/trpc.ts` 里现有的全局 toast 只处理查询错误，增删改的错误在各自的地方处理。
- UI 组件：用 `packages/ui` 中的 shadcn 组件，需要补充 table、dialog、alert-dialog、badge、avatar、pagination、select 等（`npx shadcn@latest add <组件> -c packages/ui`）。
- 每个页面都要处理加载中、空数据、出错三种状态。

## 7. 接口设计（tRPC，`githubUser` 路由）

所有接口都使用 `protectedProcedure`，输入用 Zod 定义。

| 接口 | 类型 | 输入 | 输出 | 常见错误 |
| --- | --- | --- | --- | --- |
| `githubUser.search` | query | `{ q, page?: number }`，`page` 默认 1，最大 100 | `{ items: [{ githubId, login, avatarUrl, htmlUrl, savedId, exactMatch }], total, page, hasMore }`，`savedId` 未保存时为 `null` | `BAD_REQUEST` `TOO_MANY_REQUESTS` `BAD_GATEWAY` |
| `githubUser.lookup` | query | `{ username }` | 完整 GitHub 资料 + `savedId`，不写数据库 | `BAD_REQUEST` `NOT_FOUND` `TOO_MANY_REQUESTS` `BAD_GATEWAY` |
| `githubUser.create` | mutation | `{ username }` | 新建的记录 | `BAD_REQUEST` `NOT_FOUND` `CONFLICT` `TOO_MANY_REQUESTS` `BAD_GATEWAY` |
| `githubUser.list` | query | `{ q?, tag?, sort?: "createdAt" \| "followers" \| "syncedAt", order?: "asc" \| "desc", page?, pageSize?: 10 \| 20 \| 50 }` | `{ items, page, pageSize, total }` | `BAD_REQUEST` |
| `githubUser.byId` | query | `{ id }` | 单条记录 | `NOT_FOUND` |
| `githubUser.tags` | query | 无 | 所有用过的标签（列表的标签筛选用） | |
| `githubUser.update` | mutation | `{ id, remark?: string \| null, tags?: string[] }` | 更新后的记录 | `BAD_REQUEST` `NOT_FOUND` |
| `githubUser.sync` | mutation | `{ id }` | 同步后的记录 | `NOT_FOUND` `TOO_MANY_REQUESTS` `BAD_GATEWAY` |
| `githubUser.delete` | mutation | `{ id }` | `{ id }`，物理删除 | `NOT_FOUND` |
| `githubUser.deleteMany` | mutation | `{ ids }`，最多 100 个（P1） | `{ count }` 实际删除的数量，物理删除 | `BAD_REQUEST` |

补充说明：
- `githubUser.search`：GitHub 最多只返回前 1000 条结果，所以 `page × 10` 超过 1000 时返回 `BAD_REQUEST`。`exactMatch` 为 `true` 的条目排在本页第一位。
- `githubUser.create`：遇到重复时，先按 `githubId` 查，查到就返回 `CONFLICT`；同时用 Prisma 的唯一约束错误（`P2002`）兜底，防止两个请求同时添加同一个人。

## 8. 非功能需求
- **安全**：
  - `GITHUB_TOKEN` 只放在 `apps/server`，不会发到前端。
  - 本功能所有接口都使用 `protectedProcedure`。
  - 开放注册带来的风险：任何人注册后都能修改和删除全部数据，也会消耗共用的 GitHub 额度。本期接受这个风险，用注册限流降低滥用，并在 README 中写明。
  - CORS 只允许 `CORS_ORIGIN` 指定的来源（已有）。
  - 前端展示简介、博客等外部内容时，不使用 `dangerouslySetInnerHTML`；外链加上 `rel="noopener noreferrer"`；博客地址只接受 `http` 和 `https` 开头的链接。
  - 头像用 Next.js 的 `<Image>` 组件，并在 `next.config.ts` 的 `images.remotePatterns` 中允许 `avatars.githubusercontent.com`。
- **性能**：列表接口 P95 小于 300ms（不含 GitHub 调用）。
- **可靠性**：GitHub 调用失败只影响搜索、资料查询、添加和同步，不影响列表、详情、修改和删除。
- **测试**：
  - 引入 Vitest。
  - GitHub 客户端：用模拟的 `fetch` 覆盖搜索和资料查询的成功、404、两种限流、422、超时、返回数据格式异常、缓存命中等情况。
  - `githubUserRouter`：通过 `createCaller` 测试各接口的输入校验、权限和业务逻辑，包括删除后重新添加同一用户。
- **代码质量**：`pnpm run check` 和 `pnpm run check-types` 通过。
